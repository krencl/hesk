# ADR 0023: Shared game catalog

Status: accepted (2026-10-22)

## Context
A game belonged to a single party (`game.party_id`), so the same game (say Vládce Tokia, i.e. King of Tokyo) existed in the database as many times as there are parties playing it, and an administrator of several parties had to edit it in several places. In the old application and on BoardGameGeek, games are one common database. Goal: one big database of games maintained only by game administrators, from which a party merely "enlists" games.

## Decision
- **`game` is a global catalog** (no `party_id`): name, short name, scoring, cover, description, cheatsheet, `bgg_id`, expansions and characters are common to all parties. `bgg_id` is **unique** (a game from BGG is in the catalog at most once).
- **`party_game (party, game)`** (entity `PartyGame`, unique `(party_id, game_id)`) is the link between a game and a party. It also holds the **game's own players** (`party_game_player`, formerly `game_player`, ADR 0019), because players are members of a specific party. `Party::addGame/removeGame/hasGame/findGameLink` replace queries on `game.party`.
- **Plays, sessions, tags and statistics stay per party**: `play` points to the global game and the party, statistics and a game's last play are computed only from plays of the given party (`GameRepository::statsFor(party, games)`). A play may only be created for a game enlisted in the party.
- **No duplicates.** When adding a game, the search offers first the party's games ("Už v partě", already in the party), then other games of the catalog ("Z lokální databáze", from the local database), then the cache and BGG; the same `bgg_id` is never offered twice. **Picking a game from the catalog enlists it in the party right away** (`POST /api/parties/{id}/game-links {gameId}`, idempotent), with no form and no new game. A new game in the catalog is created only from BGG (a form with cover cropping) or as a **custom game without `bgg_id`** (the exception). `POST /api/parties/{id}/games` rejects a duplicate (422): the same `bgg_id`, for a custom game the same name (case-insensitive); the same applies on edit (`GameRepository::findDuplicate`).
- **Permissions:** shared game data may be edited (`PUT /api/games/{id}`) and deleted (`DELETE /api/games/{id}`, only a game without plays in any party) only by a **game administrator** = a user with the role `ROLE_GAMES_ADMIN` (`user.roles`, JSON; in `GET /api/me` as `roles`). The role is granted by `php bin/console app:user:role <e-mail> [ROLE] [--remove]`. A party's games are managed by the **recorder and party administrator** (`PARTY_WRITE`): create a game (new from BGG/custom), enlist it in the party, remove it from the party (`DELETE /api/parties/{id}/games/{gameId}`, not when it has plays in the party; the game stays in the catalog), upload a cover and change the party game's own players (`PUT /api/parties/{id}/games/{gameId}/players`). An ordinary member only reads games (list, detail, search) and sees neither "Spravovat hry" (Manage games) nor adding a game (`RequireWriter`). Management of game administrators (UI) is deliberately postponed.
- **Game detail is in the context of a party:** `GET /api/parties/{id}/games/{gameId}` (404 if the game is not in the party); `GET /api/games/{id}` removed.
- **Game form** (`/games/:id/edit`): a non-administrator sees the shared fields locked (`<fieldset disabled>`) and saves only the game's players; an administrator saves the shared data (`PUT /api/games/{id}`) and then the players. At the bottom are "Odebrat z party" (Remove from party) and (administrator) "Smazat hru z databáze" (Delete game from the database).
- **Import from the old application** (ADR 0012) creates each game once (matched by name, case-insensitive; the `legacy_map` link keys are the plain old ids of games, expansions and characters) and enlists it in the parties where it was played; the game's own players are assigned in those parties.
- **Migration** `Version20261027000000` converts the existing games 1:1 (each stays in its party, `game_player` → `party_game_player`) and is irreversible (`down` throws an exception). Merging identical games from different parties is left to a new import from the old application (the data is wiped before it; the old games had duplicates only because of the old model).

## Consequences
- Edits to a game show up in all parties; members of other parties cannot affect them (only a game administrator can).
- Covers and cheatsheets are no longer per party. A game removed from a party remains in the catalog (a game without a party can be deleted by an administrator).
- Games with the same name and a different `bgg_id` (different games) may exist in the catalog; only a custom game without `bgg_id` is guarded.
- ADR 0021: a game from another party is no longer prefilled into the form (`prefill` removed), the search response carries `gameId` and `imageUrl`.
