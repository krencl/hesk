# ADR 0012: Repeatable import from the old application

Status: accepted (2026-10-16), import code removed (ADR 0029, last commit containing it `a4d9414`)

## Context
The first import (ADR 0007) was a one-off migration over `legacy_*` copies of tables. The old application, however, is still in use and its database (`hesk-old`) keeps changing (on the day of introduction: 731 plays instead of 544, 108 games instead of 81). We need to transfer the data into the new database (`hesk`) repeatedly until the switch-over.

## Decision
- **Command** `php bin/console app:legacy:import [--dry-run] [-v]` (`ImportLegacyCommand` + `App\Legacy\LegacyImporter`). It is recommended to run it with `--no-debug` (otherwise the profiler remembers all queries) and with `--dry-run` first; `-v` prints changed values.
- **Credentials** for the old DB live only in the environment variables `LEGACY_DB_HOSTNAME`, `LEGACY_DB_PORT`, `LEGACY_DB_DATABASE`, `LEGACY_DB_USERNAME`, `LEGACY_DB_PASSWORD`. Real values belong in `backend/.env.dev.local` (git-ignored); the committed `backend/.env` has only empty keys. The connection to the old DB is opened with `SET SESSION TRANSACTION READ ONLY` and refused if the source is identical to the target.
- **Synchronization, not loading from scratch.** The table `legacy_map (entity, legacy_key, new_id)` holds the "old → new" link (created automatically; the `legacy_*` name is ignored by `schema_filter`). On the next run, items are updated according to the link, new ones are inserted, and plays/results deleted in the old application are deleted. The lists of games, players, tags, expansions and characters are not deleted (they are shared and may have links).
- **Adoption:** if a link is missing (first run after the one-off migration, or loss of the table), existing rows are adopted by natural keys: e-mail (user), id + name (party), name in party (player, game, tag), name in game (expansion, character), (party, number) (session), id + party (play), (play, player) (result). Nothing is duplicated.
- **What the import owns:** names, scoring types, short names, cheatsheets, the game's own player, expansions and characters, sessions (number and boundaries), plays (time in Europe/Prague → UTC, note, expansions, tags) and results (score, rank, winner, starting player, character).
- **What the import does not overwrite:** the nickname and Google account of an existing user (it only fills in missing ones), the creation date of existing rows (in the old DB it is often "today" after a restore), names of players linked to an account, the game description, and anything created only in the new application (rows without a link). New plays from the new application do not collide: the old play id is used only if it is free.
- **Game covers:** the import does not copy them and does not overwrite `image_url`; images are uploaded in game management (ADR 0020, the original copying of covers to `/static/covers/` is gone).
- The whole run is a single transaction; `--dry-run` rolls it back and prints what would change.
- **Full reset:** `php bin/console app:legacy:reset [--yes]` (`ResetLegacyCommand`, `dev` only) verifies that the old DB can be read (`app:legacy:import --check`, before anything is deleted; a dry-run import would run over the existing data and could fail on a session uniqueness constraint because of changes made in the new application, e.g. play moves, ADR 0028), backs up roles and game covers (`var/legacy-reset-backup.json`; the old DB does not have them), drops the database, runs the migrations and the import and restores roles and covers (games by `bgg_id`, otherwise by name). Each step runs on a clean connection – DDL in MariaDB commits transactions implicitly, and the import would otherwise end with the error "There is no active transaction" in the same process.

## Consequences
- As long as the old application is in use, plays in it are the source of truth: edits of imported plays and results in the new application are overwritten on the next import. After the switch-over the command stops being run (and the `legacy_map` table and `legacy_*` can be deleted).
- Games and players are created only in parties where they were played (as before); a play deleted in the old application also deletes the session that thereby became orphaned.
- The command is covered by functional tests (`LegacyImportTest`): first import, repeat without changes, update and deletion, adoption after loss of links, dry run, id collision and preservation of accounts.
