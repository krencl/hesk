# ADR 0021: Creating games via BoardGameGeek

Status: accepted (2026-10-21)

## Context
A new game was an empty form (name, scoring, image, …). The main source should be BoardGameGeek (BGG XML API2): the user enters only the name, the game is found and pre-filled. A custom game may be created only when none is found.

BGG XML API2 **requires a registered application and a token** (`Authorization: Bearer`, requests to `boardgamegeek.com` without `www`); approval of the application at https://boardgamegeek.com/applications can take a week or longer. I could not load the official terms page from the development environment (403), so the details (limits, license, attribution) must be verified at registration; the UI has a link "Data her poskytuje BoardGameGeek" (Game data provided by BoardGameGeek).

## Decision
- **The first step of a new game is just the Název (Name) field** (`BggGameSearch`, `/games/new`). The game form (unchanged, only with `bggId`) is shown after picking a result, or after "Založit vlastní hru" (Create custom game); that is offered only after the search has finished (≥ 2 characters, debounce) and pre-fills the entered name. Editing a game (`/games/:id/edit`) starts directly with the form.
- **Order of sources** (`BggCatalog::search`, `GET /api/parties/{id}/game-search?q=`): 1) party games (local DB; a game with `gameId` is only a link "Už v partě" (Already in the party), so that duplicates are not created), 2) games from other parties (`source: catalog`, the same `game` table; one per name, preferring one with `bgg_id` and an image, and not one whose name or `bgg_id` the party already has; the result carries no `gameId` and carries `prefill` – short name, scoring and local image –, so picking it pre-fills the form without a server request and a new game is created in the party; description, cheatsheet, expansions and players are not taken over), 3) local BGG cache (`bgg_game`, shared between parties; only name, year and image address), 4) live BGG API. The API is called only when the first three sources together give fewer than `LOCAL_ENOUGH` (5) results; what it returns is saved to the cache. Duplicates are recognized by `bggId`. The response carries `bgg: used | skipped | unavailable`; when unavailable (no token, error, 429) the local results remain and the UI announces it – a custom game can always be created.
- **Picking a game** (`POST /api/parties/{id}/bgg/import {bggId}`) returns `{bggId, name, bggImageUrl}`; `bggImageUrl` is the original on the BGG CDN. If a game with an address is already in the cache, BGG is not called. Description, expansions etc. are not taken over (the BGG description is a long English text); scoring stays at the default "most points" and is fine-tuned in the form.
- **Image:** the server **does not store it**. The form shows a live preview from the CDN and immediately opens the crop popup from ADR 0020; only the **crop** is uploaded via the existing `POST …/game-images` and stored locally as WebP. A cancelled crop leaves the preview and the button "Oříznout obrázek z BGG" (Crop image from BGG); an uncropped image is not stored with the game (`image_url` may still only be `/uploads/covers/…`). A canvas must not read an image from a foreign origin without CORS (and I did not verify the CDN headers), so the crop loads the image through the proxy `GET /api/bgg/image?url=` (logged-in users only; only `https` on `geekdo-images.com` and subdomains, no redirects and ports, max. 10 MB, the type is determined by content).
- **Model:** `game.bgg_id` (nullable, sent by the form also when editing; a link to BGG in the form) and the table `bgg_game` (`bgg_id` unique, `name`, `published_year`, `image_url` = CDN address, `fetched_at`). The cache has no expiration yet.
- **Configuration:** `BGG_API_TOKEN` in `.env.local`/environment (empty = not set; then only the party and the cache are searched). `BggClient` parses XML via `ext-dom` and uses `symfony/http-client`; in tests it is replaced by `FakeBggClient`, the format of BGG responses is verified by `BggClientTest` on sample XML.

## Consequences
- **Not tried live:** until the application is approved at BGG and a token is inserted, the real API could not be called (the XML shape is based on documentation/examples) nor the image CDN address verified; the first live run must be checked (search, `thing`, image proxy, crop).
- Cache without expiration: changes of names/images on BGG are reflected in it only on a new search (name, year) or not at all (image address).
- The image proxy is the only path through which the server downloads foreign content; the host restriction is in `BggClient::fetchImage`.
- Games created earlier have no `bgg_id`; a BGG link can be added to them only by creating anew (no "pairing" of an existing game yet).
- Searching games from other parties reveals to party members the names (and short names, images) of games of other parties; no other data is returned.
- **Path rename** (2026-10-22): the search is `GET /api/parties/{id}/game-search` (originally `…/bgg/search`), because the primary source is the local database and BGG is only the last step. Under `…/bgg/` remain only taking over a game from BGG (`POST …/bgg/import`) and the image proxy (`/api/bgg/image`).
- **Shared catalog** (ADR 0023, 2026-10-22): source 2 is all games of the catalog that the party does not have; the result carries `gameId` and `imageUrl` (no longer `prefill`) and picking it **directly adds the game to the party** (`POST /api/parties/{id}/game-links`), it does not create a new one. `imageUrl` is returned for all results (local or from the BGG CDN from the cache; for live search it is usually `null`).
