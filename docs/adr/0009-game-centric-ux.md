# ADR 0009: UX Based on the Prototype – Game-Oriented Application

Status: accepted (2026-10-14)

## Context
ADR 0008 took over only the look of the prototype (`/hesk-dev-old`); the home page remained a chronological list of plays. The owner wants the application to resemble the prototype in its controls as well. The prototype is **game-oriented**: it opens with a list of games (cover, name, last play and winner), with search and a filter; the game detail shows its plays and the cheatsheet; a play is created from the game detail.

## Decision
- **Routes:** `/` (game list; since 2026-10-23 directly at the root, the old `/games` redirects to `/`), `/games/:id` (game detail with plays), `/games/:id/cheatsheet`, `/games/:id/edit`, `/games/new`. Game management is at `/manage/games`: search and filter (sorting) as in the game list, default sorting by name, lazy loading; it shares `GameSearch` and `useGameList` with it, the settings are remembered separately. A play is created only from the game detail: `/games/:id/new-play` (the game is given, it is not selected in the form); after saving we return to the game detail. The standalone chronology of plays (`/plays`) and the generic form `/plays/new` with game selection were removed as redundant (2026-10-16); the play detail `/plays/:id` remained.
- **Game list:** search in the name, filter (Sorting: activity / name; Session: session number), further pages of 20 are fetched while scrolling (lazy loading, the `LoadMore` component with `IntersectionObserver`; the "Načíst další" (Load more) button remains only as a fallback without an observer and "Zkusit znovu" (Try again) after an error); the settings survive returning from a page (`sessionStorage`). The backend `GET /parties/{id}/games` takes `q`, `sort`, `sessionNumber`, `limit`, `offset` and returns `lastPlay` (date, session number, winners) and `playCount`. Pagination without a total count: the client requests `limit+1` records and uses that to detect another page.
- **Game detail:** the game's plays from newest (`GET /parties/{id}/plays?gameId=`), the first one expanded, expanding shows the game version (expansion), session number, tags, note and results; deletion with confirmation. Buttons New play / Cheatsheet (only if it exists) / Back.
- **Session number** (`game_session.number`, unique within a party): the old application had the number maintained manually and with gaps (party 1: 66 sessions, numbers up to 69), so chronological ordering would show different numbers than the prototype. The migration `…20261014000000` takes the number from `legacy_round`, otherwise numbers chronologically; a new session gets `max+1`. Plays return `sessionNumber`, `GET /parties/{id}/sessions` returns the list of sessions for the filter.
- **Cheatsheets are Markdown:** the prototype stored them as Markdown (`marked`), the import took them over unchanged. The UI renders them via `marked` and always sanitizes the output (DOMPurify); because Markdown lets HTML through, this works for hand-written HTML as well. The data does not change.
- **Game covers:** the prototype served them from files (`web/public/img/cover/`), the import did not carry over `cover_image`. In the dev environment the files were copied to `frontend/public/covers/` (git-ignored, ~13 MB; today only as a backup in `/legacy-covers/covers/`, see ADR 0020) and `game.image_url` is set to `/static/covers/<file>`. This is local data, not a feature – the proper solution is image upload (ADR 0020, the files were re-migrated to `web/uploads/`).
- Small things from the prototype: a pulsing ring around the party button while loading, skeletons instead of "Načítám…" (Loading…), a menu with sections Parta (Party) / Menu / Správa (Management) and an underlined logout, the winner icon `workspace_premium`.

- **Party: management and detail are separate** (2026-10-16): `/parties` = party management (list, switching the active one, creating a new one; after creation its detail opens), `/parties/:id` = party detail (members, role changes, removal, invitations, leaving). Menu: "Zobrazit detail" (Show detail) leads to the detail of the active party, "Spravovat party" (Manage parties) to management. The detail can also be opened for an inactive party.

- **Play editing instead of play detail** (2026-10-16): the play detail page (`/plays/:id`) was removed (it added nothing to the expanded play in the game detail). The expanded play has a single button "Upravit" (Edit) → `/plays/:id/edit`, the form shared with play creation (`PlayForm`); "Smazat zápis" (Delete play; with confirmation) is only below the edit form. A game can be edited only from game management (`/manage/games` → `/games/:id/edit`), the link from the game detail disappeared.

## Consequences
- The old link `/games/:id` (game form) now leads to the detail; the form is at `/games/:id/edit`.
- The default sorting of `GET …/games` changed to "last activity" (game management requests `sort=name`).
- When sessions change (deleting a play, moving), the numbers of other sessions stay unchanged; a number freed by deleting the last session is reused.
